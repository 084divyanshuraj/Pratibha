# Smart Campus Analytics — Backend Product Requirements Document

**Version:** 1.0  
**Product area:** Backend API + MongoDB  
**Primary stakeholders:** Institution administrators, faculty, placement officers, students, frontend team and ML team.

## 1. Problem statement

College data is spread across academic systems, attendance, LMS, engagement activities, placement assessments, skills evaluations and feedback. The platform needs a consistent backend layer to integrate these data, calculate explainable indicators, identify potential academic/placement risks, and coordinate supportive interventions.

The backend must power two portals with different permissions and also provide stable interfaces for a separate ML inference service. A signature capability is the Intervention Sandbox, which compares potential support plans under explicit resource constraints.

## 2. Product goals

1. Provide one unified, permission-aware view of student information.
2. Expose all seven problem-statement data categories through consistent APIs.
3. Calculate a documented Student Success Score on the server.
4. Store and expose risk predictions generated by the agreed ML service or transparently labelled rules.
5. Power institutional analytics and student segmentation.
6. Let authorized staff create, compare and approve deterministic intervention scenarios.
7. Track assigned interventions and observed progress/outcomes.
8. Provide clear integration contracts so frontend and ML development can proceed independently.
9. Deploy as an Express service on Render using MongoDB Atlas, with a separate Python/FastAPI inference service.

## 3. Non-goals for the initial backend

- Training ML models inside the Node.js backend.
- Building frontend screens or chart components.
- Claiming a causal treatment effect from ordinary predictive scores or before/after data.
- Connecting to real college SIS/LMS systems without approved access and documentation.
- Implementing a complex microservice mesh or event streaming platform for the initial hackathon prototype.
- Choosing an LLM provider before the team approves one.
- Treating risk flags as definitive decisions about students.

## 4. Users and authorization

### Administrator (`admin`)
Manages user provisioning, data imports and high-level configuration; sees institution-wide aggregates and authorized records; approves interventions/scenarios.

### Faculty (`faculty`)
Views authorized student records, academic indicators and support interventions for the permitted cohort. Scope should be explicit if department/course boundaries exist.

### Placement officer (`placement_officer`)
Views authorized placement/readiness indicators, skills and placement-support workflows.

### Student (`student`)
Views only their own private profile, scores, permitted predictions/readiness explanations, interventions and submits feedback. The student cannot search or enumerate other students.

Authorization must be enforced server-side for every request. Hiding a button in the frontend is not a security boundary.

## 5. Functional requirements

### FR-01: API foundation
The backend shall expose versioned REST endpoints, consistent JSON envelopes, request IDs, input validation and centralized safe error handling.

**Acceptance:** Invalid requests receive documented error responses; unknown routes are handled consistently; health endpoints work; production errors do not expose stack traces.

### FR-02: Authentication and role access
The backend shall authenticate users and enforce role/object-level access.

**Acceptance:** Missing/invalid tokens are rejected; users cannot self-assign roles; students cannot retrieve another student's records by changing the URL.

### FR-03: Unified student profile
The backend shall provide stable student identifiers and searchable, paginated profiles linked to all supported data categories.

**Acceptance:** A staff user can query an authorized student and retrieve a profile/summary linked by the same `studentId`; internal database identifiers are not the only public IDs.

### FR-04: Seven-category integration
The backend shall accept/represent academic, attendance, LMS, engagement, placement, skills and feedback records, with data-quality feedback.

**Acceptance:** Each category has a defined schema; imports report accepted/rejected/warning counts; invalid foreign IDs and bad ranges are identified; missing data is preserved as missing.

### FR-05: Student Success Score
The backend shall compute and persist a score using a documented formula, component values, version and explanation.

**Acceptance:** Formula is versioned, reproducible and documented; score components are returned; null/missing data follows an explicit rule; score is not reported as a probability.

### FR-06: Academic risk prediction
The backend shall prepare the agreed features and call the ML service for a defined academic target when an appropriate model is configured.

**Acceptance:** Feature names match the ML contract; features reflect only data available at prediction time; response includes target/model version and supported output semantics; no prediction is fabricated on service failure.

### FR-07: Placement risk/readiness
The backend shall support a defined placement-risk target or a clearly labelled readiness index according to label availability.

**Acceptance:** The selected target is documented; calibrated probabilities are only presented when supported; readiness rules are not misrepresented as an evaluated ML outcome model.

### FR-08: Institutional analytics
The backend shall provide aggregates for student counts, score distribution/averages, academic/placement risk summaries and trends from actual persisted data.

**Acceptance:** Results have explicit filters/time windows; aggregate endpoints enforce staff authorization; empty/missing data is not misrepresented as a measured zero.

### FR-09: Explainability and segmentation
The backend shall store score contributors and expose meaningful segment definitions/membership.

**Acceptance:** Explanations tie to observed indicators/thresholds or supported model explanation; segment rules have versions; segments are supportive rather than stigmatizing.

### FR-10: Intervention catalog and assignments
The backend shall manage available interventions, assign them to students, and record progress/outcomes.

**Acceptance:** Status transitions are validated; assigned student and approving actor are tracked; outcomes have timestamps and remain distinct from predictions.

### FR-11: Intervention Sandbox
The backend shall compare intervention plans within explicit eligibility and capacity constraints.

**Acceptance:** Scenario output includes strategy, constraints, selected and excluded records with reasons, resource use, rule version and assumptions; assignments require permitted approval; no made-up uplift or unsupported causal claim is returned.

### FR-12: Feedback
The backend shall accept student feedback and expose appropriately aggregated summaries to authorized staff.

**Acceptance:** Student submits feedback as themselves; raw comments are not exposed broadly; records are not automatically treated as model features.

### FR-13: ML integration boundary
The backend shall call the independent ML inference service over a configured URL and validate response schemas.

**Acceptance:** ML endpoint and timeouts are configurable; timeout/invalid output produces a stable service error; model version is persisted; frontend never calls ML directly.

### FR-14: Deployment readiness
The backend shall support Render deployment and MongoDB Atlas connectivity through environment configuration.

**Acceptance:** No committed secrets; health/readiness endpoints work; exact CORS origin is configurable; service URLs do not hardcode localhost in production.

### FR-15: Documentation and tests
The backend shall maintain API documentation, example fixtures and automated test coverage for critical behavior.

**Acceptance:** Teammates can implement against API schemas without reading backend internals; authorization, validations, ML failure and simulation limits have tests.

## 6. Data and business rules

- Stable `studentId` links source datasets; reject or report unknown references.
- Preserve provenance (source/import ID and observation time) where practical.
- A missing indicator is not an observed zero.
- Score and prediction snapshots must identify a formula/model/feature version and timestamp.
- ML features must not include information unavailable at the prediction timestamp.
- Do not use protected/sensitive attributes as scoring features without an approved lawful, fair and justified design.
- Student feedback content is access-restricted and not an automatic model feature.
- Simulation allocations obey stated capacity constraints and deterministic rules.
- Prediction, scenario estimate and observed outcome are separate data concepts.

## 7. Non-functional requirements

### Security and privacy
Authentication, least-privilege roles, object-level access control, request validation, safe logging, protected secrets and limited personal data. Apply appropriate access restrictions to feedback and audit records.

### Reliability
Centralized errors, timeouts to ML, readiness checks, predictable API contracts and graceful dependency failure.

### Maintainability
Domain-organized modular monolith, service-layer business logic, DTO mapping, versioned APIs and shared contract documentation.

### Performance
Paginated list endpoints, bounded file sizes/row counts, indexes matched to queries, bounded aggregations and no unbounded database reads. Define practical limits from the chosen demo dataset and host resources.

### Observability
Request IDs, health/readiness endpoints, structured operational logs and useful import/model error categories without unnecessary private record contents.

### Reproducibility
Version score formulas, feature schemas, model artifacts and scenario rules. Training evaluation belongs to the ML workflow and must record dataset/target/model versions.

## 8. Data acceptance and quality

Imports should validate required columns, value ranges, data types, dates, duplicate rows/IDs and stable student linkage. The import preview should identify row numbers and error reasons. A failed or partial import must not silently corrupt existing records. Import commit behavior (all-or-nothing vs per-row partial success) must be explicit and tested; for a small prototype, a documented partial-import report is acceptable.

## 9. MVP prioritization

### Must-have for Round 1
API foundation; auth/RBAC; seven categories and integrated student profiles; import/validation; documented Success Score; academic and placement risk/readiness endpoint; institutional analytics; explainable results; interventions and deterministic capacity-constrained scenario; API docs and tests; Render/Atlas deployment compatibility.

### Should-have
Segment management, intervention outcomes, import previews, aggregated feedback analytics and broader role scoping.

### Later / only after core flows work
LLM copilot, complex job queues, event-driven architecture, causal-effect estimation, large-scale model monitoring and additional integrations with institutional systems.

## 10. Dependencies and unresolved decisions

- Suitable dataset and rights/provenance.
- Target labels for academic and placement modeling.
- Final score weights, normalization and missing-data logic.
- ML feature schema, target name, response semantics and model endpoint path.
- Final cohort/department authorization rules.
- LLM provider and whether copilot is needed in the first milestone.

These must be agreed explicitly, not guessed in production-facing behavior.

## 11. Success measures

- All seven data categories can be represented and validated.
- Core APIs pass automated tests.
- Frontend can consume consistent API contracts.
- ML service can be swapped/updated without rewriting UI routes.
- Student-level access checks pass negative tests.
- Score and scenario outputs are reproducible and explainable.
- Deployed integration can execute a documented end-to-end demonstration.
